# Glossary

The terms this repo uses in a specific sense, each defined the way the document that owns it defines it, with that document's path so a reader can check the wording against the source rather than against this page. Where this page and the owning document disagree, the owning document is right and this page has a bug worth reporting (see [CONTRIBUTING.md](CONTRIBUTING.md)).

## The review and its inputs

| Term | Meaning in this repo | Defined in |
|---|---|---|
| One-line review | The block a practitioner pastes into an agent, which fetches the review map, interviews them, routes their answers to documents and writes a ranked review. It carries only what changes the agent's behaviour, and everything substantive lives in the files it fetches (Decision 1). | [README.md](README.md), [ONE-LINE-PROMPT.md](ONE-LINE-PROMPT.md), [DECISIONS.md](DECISIONS.md) |
| Fetch mode and offline mode | The two ways to run the review: fetch mode reads the files from the commit the block pins, and offline mode reads a checksummed release bundle with web fetch turned off, for assistants without fetch or behind proxies. | [ONE-LINE-PROMPT.md](ONE-LINE-PROMPT.md), [RELEASES.md](RELEASES.md) |
| Review map | `AUDIT-CONTEXT.md`, the file the agent fetches first: the interview, the reading rules for reducer output and exports, the routing section, the priority rubric and the output requirement. Its routing section is rendered from `routing.yaml` by a script and is never edited by hand. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) |
| Interview branch | The path the interview takes after its first two questions. When the organization is small or mid-sized and rents its AI, the small-org branch asks about twelve questions; every other profile gets the full branch, about five questions per surface family present. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Interview), [DECISIONS.md](DECISIONS.md) (Decision 5) |
| Size band | The first interview question: roughly how many people work at the organization and whether a sector regulator supervises its data handling, recorded as `org-size-small-mid` or `org-size-large-regulated`. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Interview) |
| Rent-or-own profile | The second interview question: whether the organization runs self-hosted model serving, fine-tuned models, or a RAG or vector store it operates, recorded as `profile-rent-heavy` if none and `profile-own-heavy` if any. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Interview), [analysis/rent-or-own-sized-to-the-org.md](analysis/rent-or-own-sized-to-the-org.md) |
| Surface (S1 to S13) | One of the thirteen places an organization's AI runs, from AI features in SaaS apps (S1) and enterprise assistants (S2) through coding agents (S4), MCP servers (S5) and direct model APIs and gateways (S8) to self-hosted serving (S9), fine-tuning pipelines (S11), RAG stores (S12) and AI inside security tools (S13). Each is placed on the CoSAI component map to show which parts are the organization's to secure. | [analysis/surface-ownability.md](analysis/surface-ownability.md) |
| Ownability | How much of a surface's component map the organization owns rather than rents or shares, grouped into bands, from surfaces where it owns little beyond identity, the enforcement point and the exported record, to surfaces where it owns every component. | [analysis/surface-ownability.md](analysis/surface-ownability.md) |
| Platform family | The category-level answer the interview asks for per surface, from a closed list (the office suite and its assistant; the managed model platform, per cloud; the coding agent; the MCP host; the browser; the identity platform; the data-governance platform). Nothing below that level is asked for. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Boundaries) |
| Observation confidence | How an answer was obtained: `read` (from a reducer or an export), `owner-stated` (from the team that owns the system) or `believed` (the person answering thinks so). A `believed` observation caps a row's priority at Medium. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Interview, Priority rubric) |
| Reducer | A standard-library script in `scripts/reducers/` that the practitioner runs on their own machine to turn an admin export into signal keys and counts, so the raw export never reaches the agent. It refuses to print any name it did not declare or any value that is not a count, true, false or `not-checked`. | [scripts/README.md](scripts/README.md) (Reducers), [DECISIONS.md](DECISIONS.md) (Decision 6) |
| Answers Block | The YAML the agent writes after the interview, one entry per signal key with its value and observation confidence, which is then matched against `routing.yaml`. The three folders in `fixtures/` are worked examples. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Answers Block), [fixtures/README.md](fixtures/README.md) |

## Routing and ranking

| Term | Meaning in this repo | Defined in |
|---|---|---|
| Signal (signal key) | One row under `signals:` in `routing.yaml`: a key, the interview question that sets it, how it is collected, its weight, its priority and the documents it routes to. | [routing.yaml](routing.yaml), [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Routing) |
| Family | The group a signal belongs to (profile, surface, record, identity, coding-agent, mcp and so on), which is the unit the interview asks about one at a time, gives a row its default sequence group in the ordering perspectives, and names the role a Question Packet is addressed to. | [routing.yaml](routing.yaml) (`family-owners`), [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Interview, Priority rubric) |
| Weight: PROBLEM, REVIEW, INVENTORY | PROBLEM produces an action and is the only weight that can take a top-action slot in the Next 30 days section; REVIEW is listed after the PROBLEM rows with the matched answer quoted and becomes a PROBLEM only where its escalation says so; INVENTORY enables other rows and fetches nothing on its own. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Routing) |
| Priority band and factors | Priority is how bad the condition is if true, scored per row from four factors of 0 to 2 each (reach, stakes, reversibility, blast radius). A sum of 6 to 8 is High, 3 to 5 Medium and 0 to 2 Low. Priority never comes from the evidence tier. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Priority rubric), [DECISIONS.md](DECISIONS.md) (Decision 3) |
| Effort (S, M or L) | A document's rough size for each practice in its summary, small, medium or large, as the document's author judges it. No file in the repo converts the letters to hours, so the review prints the letter and no hour figure. | [analysis/CANONICAL-DOC-TEMPLATE.md](analysis/CANONICAL-DOC-TEMPLATE.md), [ONE-LINE-PROMPT.md](ONE-LINE-PROMPT.md) (Structured Output Format) |
| Escalation (`escalate-if`) | A machine-readable condition on a row that raises it, for example a REVIEW row becoming a PROBLEM, and that applies only when every name in it was observed. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Routing) |
| Ordering perspectives | The author's four stated views in `analysis/decision-sequence.md`, Tier D, and the eight sequence groups written from them, which order actions inside a priority band after factor sum and before row position. They order actions and never raise one. | [analysis/decision-sequence.md](analysis/decision-sequence.md), [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Priority rubric) |
| Always Fetch documents | The four documents every review reads whatever the answers: `analysis/evidence-tiers.md`, `analysis/surface-ownability.md`, `analysis/revalidation-and-pins.md` and `analysis/decision-sequence.md`. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Routing), [routing.yaml](routing.yaml) (`always-fetch`) |
| Anti-Bloat Rule | The fetch budget applied per surface family pass, then one merge pass across families, with a fixed drop order (overlapping rows, then adjacent docs) that never drops an Always Fetch document or an unsure answer. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Anti-Bloat Rule) |
| Not checked | The status of any signal the practitioner could not supply. It is reported as not checked, never as clean, and becomes a Question Packet. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Special keys) |
| Question Packet | A category-level question addressed to the role that owns the system, produced for every not-checked, unsure or believed-only answer to a row that applies, so a gap in the interview turns into a request rather than a silence. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Routing, Special keys) |
| Convergence gate | The rule that a recommendation proposing new infrastructure is adopted only when its backing practice is `converged`, or when the organization accepts the risk explicitly; the agent never grants that exception itself. | [AUDIT-CONTEXT.md](AUDIT-CONTEXT.md) (Convergence gate) |
| Reference mapper | `scripts/route.py`, which turns an Answers Block and any reducer output into the branch, ranked actions, doc list and Question Packets, so an agent's routing can be checked against code. CI runs it against three golden fixtures. | [scripts/README.md](scripts/README.md), [fixtures/README.md](fixtures/README.md) |

## Evidence and currency

| Term | Meaning in this repo | Defined in |
|---|---|---|
| Evidence tier (A to D) | Confidence in a claim: A for standards, statute, court and regulator text and peer-reviewed research; B for practitioner work, first-party lab measurement and vendor documentation of what a feature does; C for vendor claims about how well a product works, with the bias flagged; D for one author's judgement or a model with stated assumptions, labelled as a hypothesis. Compound labels are carried, never collapsed. | [CONTRIBUTING.md](CONTRIBUTING.md) (Evidence tiers), [analysis/evidence-tiers.md](analysis/evidence-tiers.md) |
| Convergence | How broadly a practice is adopted, recorded in each document's frontmatter. Every document is born `single-source`, and becomes `converged` only through the standards route or the weekly review's check. | [analysis/evidence-tiers.md](analysis/evidence-tiers.md), [DECISIONS.md](DECISIONS.md) (Decision 7) |
| Standards route | The one way a document can be born `converged`: a published standard, statute or schema prescribes the practice and at least one independent implementation exists. | [CONTRIBUTING.md](CONTRIBUTING.md) (Integration checklist), [DECISIONS.md](DECISIONS.md) (Decision 7) |
| Pins | The framework, schema, protocol and catalogue versions the repo was checked against, listed in the frontmatter of `analysis/revalidation-and-pins.md` and copied into each release row. Other documents that pin an older version of the same name are counted as behind, which is a revalidation task rather than a failure. | [analysis/revalidation-and-pins.md](analysis/revalidation-and-pins.md), [scripts/README.md](scripts/README.md) (`check-pins.py`) |
| `revalidate-by` | The date by which a document must be re-read, staggered between three and eight months at birth, and three for anything that depends on MITRE ATLAS. | [CONTRIBUTING.md](CONTRIBUTING.md) (Integration checklist), [DECISIONS.md](DECISIONS.md) (Decision 11) |
| `measurement-claims` | Frontmatter entries for claims something can re-run, each with its source pinned to a commit, release or dated primary and its own revalidation date; judgements carry a dated prose marker instead. | [CONTRIBUTING.md](CONTRIBUTING.md) (Integration checklist), [DECISIONS.md](DECISIONS.md) (Decision 10) |
| Stub and declared gap | A stub is a short document for a family the release does not yet research, which names the standard to read meanwhile and declares the gap, so silence in the review does not read as clean. A declared gap is the machine-readable `Gap: ... Needs:` line a document uses for a claim it cannot yet back. | [DECISIONS.md](DECISIONS.md) (Decision 14), [CONTRIBUTING.md](CONTRIBUTING.md) (Declaring a gap) |
| Follow and retire toward | The two lanes a document moves through when an external standard or project comes to carry its argument: it follows the canon and stops growing where the canon covers it, and it retires toward a replacement that is supported, generally available, covers its slice and is citeable. | [CONTRIBUTING.md](CONTRIBUTING.md), [ABSORPTION-MAP.md](ABSORPTION-MAP.md) |
| Routable document | A top-level `analysis/*.md` file with status `PRODUCTION` or `EMERGING`, excluding the template; this is what the README's count line counts. | [scripts/README.md](scripts/README.md) (The README count line) |

## Releases

| Term | Meaning in this repo | Defined in |
|---|---|---|
| Release and correction release | A release is a frozen, tagged commit, `vYYYY.MM`, monthly at most. A correction that cannot wait ships as `vYYYY.MM.N`, changes no routing behaviour and moves no golden. | [RELEASES.md](RELEASES.md), [DECISIONS.md](DECISIONS.md) (Decision 17) |
| Pinned commit | The full commit SHA the one-line review's URL names, because a branch or a tag can move and a commit cannot. `RELEASES.md` records which release each SHA belongs to. | [RELEASES.md](RELEASES.md), [DECISIONS.md](DECISIONS.md) (Decision 17, which keeps Decision 2's pin) |
| Offline bundle | The concatenated release file offline mode reads, built deterministically from the tagged commit, with its SHA-256 recorded in `RELEASES.md`. | [RELEASES.md](RELEASES.md), [scripts/README.md](scripts/README.md) (`build-release-bundle.sh`) |
